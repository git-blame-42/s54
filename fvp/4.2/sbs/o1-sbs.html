Pedido típico: "uma página na área administrativa que liste só os Eventos lotados, em GET /admin/events/full (admin.events.full), com link na listagem". Chance: média-alta. Tempo: 20-30 min.

Exemplo pronto: fvp/4.2/exemplos/o1-rota-eventos-lotados/ (patch, bundle e árvore projeto/). Sem pré-requisito: sai de main. Schema não muda. O teste de acesso por HTTP da rota nova é o cenário S2 (s2-teste-acesso-rota-nova), empilhado sobre este.

1. config/routes.php

No grupo admin (linhas ~25-35), logo depois da rota new e antes de /admin/events/{id}:

        Route::get('/admin/events/new', [AdminEventsController::class, 'new'])->name('admin.events.new');
        Route::get('/admin/events/full', [AdminEventsController::class, 'full'])->name('admin.events.full');
        Route::post('/admin/events', [AdminEventsController::class, 'create'])->name('admin.events.create');

E o comentário do bloco passa a citar as duas rotas fixas:

        // Eventos (CRUD RESTful). 'new' e 'full' vêm antes de '{id}', senão seriam capturados como id.

Por quê:

  • Router casa na ordem de declaração. Depois de {id}, full vira id e cai em "Evento não encontrado!".
  • Dentro de middleware('auth') + middleware('admin'): herda os dois middlewares, nada a fazer no controller.
  • Nome no padrão admin.events.*: é o que a view usa em route().
  • Só existem get, post, put, delete em core/Router/Route.php (não há patch).

Armadilha: o teste de controller chama a ação direto, sem Router, e não pega rota depois de {id}. Só teste por HTTP pega (S2).

2. app/Models/Event.php

Método estático novo depois de availableSpots() e antes de hasEnrollments() (linha ~142):

        return max(0, (int) $this->capacity - $this->enrollmentsCount());
    }

    /**
     * Eventos lotados (sem vagas disponíveis), na ordem do banco.
     *
     * @return array<static>
     */
    public static function full(): array
    {
        return array_values(array_filter(
            static::all(),
            fn(Event $event) => $event->availableSpots() === 0
        ));
    }

Por quê:

  • "Lotado" é regra de negócio do Evento: mora no model; controller fica com uma linha.
  • Reaproveita availableSpots(): mesma conta da tela de detalhes e da validação de capacidade. Sem SQL novo, sem duplicar a regra.
  • array_values: array_filter mantém as chaves; sem ele $events[0] pode não existir.
  • @return array<static>: phpstan sabe o tipo dos itens.

Obs: o catálogo põe o mesmo array_filter direto na ação full(). Funciona igual; model é a resposta segura pra "regra no model".

Armadilhas (resumo)

  • Rota depois de /admin/events/{id}: full vira id, 302 com "Evento não encontrado!". Teste de controller não pega (chama a ação direto); só HTTP com admin logado (S2) ou Cest.
  • Sem sessão a resposta é 302 nos dois casos: teste HTTP tem de logar o admin (loggedClient).
  • $title fora do compact: layout quebra.
  • Nome fora do padrão admin.events.*.
  • array_filter sem array_values: $events[0] pode não existir.
  • availableSpots() usa max(0, ...): Evento com mais Inscrições que vagas também conta como lotado (desejado).
  • Tabela de ligação é event_user (model Enrollment), não enrollments.
  • Variante POST .../duplicate (P6): form com method="post"; PUT/DELETE exigem _method (core/Http/Request.php).
