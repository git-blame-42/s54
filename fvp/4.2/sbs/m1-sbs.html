1. database/schema.sql

Em CREATE TABLE events, logo após capacity:

    capacity    INT NOT NULL,
    workload_hours INT NOT NULL,

Por quê:

  • ActiveRecord do framework não cria coluna sozinho. save() insere todas as chaves de $columns; coluna ausente -> Unknown column.
  • NOT NULL sem DEFAULT: a validação fica no model, não no banco. DEFAULT não ajuda: o framework manda NULL quando falta valor.

Armadilha: os testes recriam o schema sozinhos; o banco de desenvolvimento não. No fim, ./run db:populate, senão o erro aparece só no navegador.

2. app/Models/Event.php

Três pontos.

a) Docblock da classe, depois de @property int|string $capacity:

 * @property int|string $workload_hours carga horária, em horas

Por quê: atributos são dinâmicos (__get/__set). Sem o @property o phpstan reclama de propriedade desconhecida. int|string porque o form manda string.

b) $columns, depois de 'capacity',:

        'workload_hours',

Por quê: é a lista que o Model usa pra montar INSERT/UPDATE e pra aceitar atribuição. Esquecer -> Property workload_hours not found e a coluna nunca vai ao banco.

c) validates(), no fim do método, depois do bloco if de capacity:

        if (Validations::notEmpty('capacity', $this) && Validations::integerMin('capacity', $this, 1)) {
            $this->validatesCapacityAgainstEnrollments();
        }

        Validations::notEmpty('workload_hours', $this) &&
            Validations::integerMin('workload_hours', $this, 1);
    }

Por quê:

  • Validação mora no model, nunca no controller.
  • && = curto-circuito: só testa >= 1 se não estiver vazio; senão duplica erro no mesmo campo.
  • Cada Validations::x grava erro em $this->errors quando falha; save() só persiste sem erros.
  • Mesmo padrão das linhas de kind/modality. Não precisa de if porque não há regra extra depois (capacity só tem if por causa do validatesCapacityAgainstEnrollments()).

3. app/Controllers/Admin/EventsController.php

Constante FIELDS (linha ~14):

    private const FIELDS = ['title', 'description', 'kind', 'modality', 'starts_on', 'location', 'capacity', 'workload_hours'];

Por quê:

  • create/update não leem $_POST. Um método privado faz foreach (self::FIELDS as $field) e copia $params[$field] pro model, como string.
  • É uma allowlist: só o que está em FIELDS sai do form e chega ao model. Protege contra user_id=1 injetado no POST (mass assignment).

Armadilhas:

  • Esquecer aqui: form envia, controller ignora, model recebe null, notEmpty reclama de vazio "sem motivo".
  • Não faça (int) $params['workload_hours'] no controller. Conversão silenciosa: "abc" viraria 0. Deixe a string ir e o integerMin rejeitar.

4. app/views/admin/events/_form.phtml

Depois do </div> do bloco de capacity, antes do <button type="submit">:

    <div class="mb-3">
        <label for="event_workload_hours" class="form-label">Carga horária (horas)</label>
        <input type="number" class="form-control<?= $invalid('workload_hours') ?>" id="event_workload_hours"
            name="event[workload_hours]" min="1" value="<?= htmlspecialchars((string) $event->workload_hours) ?>">
        <?= $feedback('workload_hours') ?>
    </div>

Cópia do bloco de capacity trocando id, name, label e value.

Por quê cada parte:

  • name="event[workload_hours]": chega como $request->getParam('event')['workload_hours']. O [...] agrupa; o controller lê o array event e passa por FIELDS.
  • $invalid(...): adiciona is-invalid (Bootstrap, borda vermelha) se $event->errors('workload_hours') existir.
  • $feedback(...): imprime a mensagem de erro embaixo do campo. Os dois helpers estão no topo do arquivo (FORM:11-14).
  • value="...$event->workload_hours": o form serve a new e edit. Em new vem vazio; em edit vem o salvo; em erro de validação vem o que o usuário digitou.
  • htmlspecialchars: rubrica cobra escape (XSS).
  • O form tem novalidate: min="1" é só UX; o erro real vem do servidor.

    public function test_create_saves_workload_hours_and_show_displays_it(): void
    {
