1. lib/Paginator.php

a) Último parâmetro do construtor, depois de $route (linha ~25):

        private ?string $orderBy = null

b) loadRegisters() (linha ~118): monte $order depois de $attributes e insira no SQL entre o WHERE e o LIMIT:

        $attributes = implode(', ', $this->attributes);
        // $orderBy vem sempre do código (controller), nunca da requisição: não há bind para ORDER BY.
        $order = $this->orderBy !== null ? "ORDER BY {$this->orderBy}" : '';

        $sql = <<<SQL
            SELECT id, {$attributes} FROM {$this->table}
            {$this->buildConditions()}
            {$order}
            LIMIT :limit OFFSET :offset
        SQL;

Por quê:

  • Ordenar no SQL é o único jeito certo com paginação: LIMIT/OFFSET corta as 5 linhas depois do ORDER BY.
  • Ordem SQL obrigatória: WHERE ... ORDER BY ... LIMIT ....
  • ORDER BY não aceita bindValue (é identificador, não valor): a string tem que vir do código, nunca da requisição.
  • loadTotals() (COUNT(*)) não precisa de ordem: não mexa.
  • Parâmetro opcional no fim: quem chama hoje não quebra.

Armadilhas (resumo)

  • usort no controller ordena só a página de 5: errado, aparece na página 2. Faça no SQL.
  • Sem desempate por id: datas iguais podem trocar de página; pode quebrar test_index_lists_five_events_per_page (mesma data).
  • Nunca interpole ?sort= em ORDER BY (SQL injection): lista fechada (['starts_on', 'title']) e in_array(..., true).
  • ORDER BY depois do LIMIT: erro de sintaxe no MySQL.
  • Event::all() também não ordena; se o pedido for sobre ele, método Event::allOrderedByDate() com SQL no model.
  • Sem ORDER BY o MySQL não garante ordem (hoje sai por id porque o InnoDB lê pela chave primária). Se só apontarem o defeito, ORDER BY id é a correção mínima e não quebra nada.
  • CreateSuccessfullyCest esperava o Evento novo na página 4: agora ele está na página 1.
